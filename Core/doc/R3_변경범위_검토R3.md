## 0. 한 줄 결론

**R3는 파라미터 개정이 아니라 제어 아키텍처 개정이고, 게다가 제로지오 측이 공정 FSM을 이미 C로 작성해 넘겼다.**

헹굼의 종료 판정 주체가 MCU 시간에서 **회로(UL1)의 가이드 감지 횟수 cnt**로 넘어가고, 불법방출 락이 **K2/K3 래치 + 3입력 AND 공통해제**로 회로에 고정된다. 여기까지는 초판과 같다.

코드 대조로 새로 확인된 것은 **전달물 안에 `controller.c` / `zg_tick()` 형태의 완성된 공정 상태머신과 `board_port.h` 포트 경계가 들어 있다**는 사실이다. 제로지오는 “시작 코드·클록·주변장치·링커·핀 적용표”(`port_contract.json` → `PLATFORM`)를 명시적으로 개발사 몫으로 남겼다. 즉 **R3의 “기존 펌웨어”는 우리 R2 코드가 맞고(§7 Q1), 우리가 결정해야 할 것은 “R2 시나리오를 R3대로 재작성할 것인가, 제로지오 FSM을 링크하고 board_port만 구현할 것인가”다.**

이 결정이 공수를 절반 이상 가른다. §0.1에서 먼저 정리한다.

## 0.1 ★최우선 결정 — 이식(A) vs 자체 구현(B)

`include/board_port.h`가 정의하는 경계는 딱 세 개다.

```c
typedef struct {
    void *context;
    bool (*read_inputs)(void *, zg_inputs *);
    bool (*apply_outputs)(void *, const zg_outputs *);
    bool (*requests)(void *, uint32_t, uint8_t, bool, bool, bool);
} zg_board_port;
bool zg_board_cycle(zg_controller *controller, const zg_board_port *port, uint32_t now);
```

| | **A안 — 이식** | **B안 — 자체 구현** |
|---|---|---|
| 우리가 쓰는 것 | `board_port.c` 구현 + 드라이버 계층 | 헹굼/건조/배출 상태머신 전체 재작성 |
| `moeum.c` · `dongjak.c` | **대체(폐기)** — 시나리오 계층이 `controller.c`로 넘어감 | 재작성 후 유지 |
| 사양 추적성 | 원본 엑셀 74단계와 자동 생성 `config.c`가 그대로 따라온다 | 우리가 매번 수동 동기화 |
| 사양 변경 대응 | 제로지오가 `sync_workbook.py`로 재생성 → 우리는 링크만 | 매 변경마다 우리 코드 수정 |
| 리스크 | 남의 코드가 제품 제어 경로에 들어온다. 검증 책임 경계가 모호 | 공수 최대. 사양 드리프트 재발 |
| 현실성 | `zg_inputs` 40여 신호 중 **R2가 지금 못 만드는 것이 12종**(§5) | 동일한 12종을 결국 만들어야 함 |

> **판단**: 어느 쪽이든 **§5의 미보유 입출력 12종은 똑같이 필요**하다. 그러므로 이 결정은 “무엇을 먼저 하느냐”가 아니라 **“시나리오 계층의 소유권을 누가 갖느냐”**의 문제이고, 인수·검증 책임 범위와 직결되므로 **기술고문·개발사 합의 사항**이다. 착수 순서(§10)는 **어느 쪽을 택해도 동일한 1~4단계**를 먼저 두도록 짰다.

## 2. 판정 주체의 이동

| 판정 | R2(현재) | R3 | 영향 |
|---|---|---|---|
| 헹굼 진행량 | `MOEUM_STIR_CYCLES`(11) / `DJ_RINSE_STIR_MS`(117000) | **UL1의 J28 가이드 감지 횟수 cnt** — 20에서 배수문 열기, 40에서 교반 정지 (`ZG_HW_WASH_EDGES 20` / `ZG_HW_TOTAL_EDGES 40`) | 시간 상수 전부 폐기 |
| 회차 정상/이상 | 없음(시간 경과=정상) | **`t_cycle ≥ 60s`**(`ZG_HW_MIN_CYCLE_MS 60000`) AND 이상이력 없음 AND 배수문 실제 열림 | 정상완료 신호 개념 신설 |
| 교반 명령 차단 | 시나리오가 직접 정지 | UL1 이상기억 → **UL4가 U30-2의 MCU 교반 명령선을 차단** | MCU는 차단을 당하는 쪽 |
| 급수 허가 | MCU가 밸브 ON/OFF | 회로 래치. **cnt=20에 회로가 허가 차단** | 명령만으로 열리지 않음 |
| 온도 락 | 60/80℃ 바이메탈 관찰만 | **K3(50℃) / K2(70℃) 래치**, 공통해제까지 유지 | 온도 하강으로 안 풀림 |
| 분쇄 허가 | **센서 온도로 SW 게이팅**(`DJ_TEMP_GRIND_ON_D10`) | **회로가 만든 `grind_allowed` 관측 + 프로그램 명령** | SW 온도 게이트 제거 대상(§7 Q3) |
| 락 해제 | 배출문 리드스위치(HW 즉시) | **타이머완료 AND 무게이력 AND 배출문 닫힘 → Init-RST** | MCU는 `common_release_authorized` 1비트만 읽는다 |
| MCU ↔ 락회로 | 직접 GPIO | **UE1(TCA9534 @0x20)** I2C 요청 포트 | 신규 경로 + 실패 예외 EX12 |

> **R3 00 시트 “구현 시 절대 조건” 5개** — ① 이상 시 프로그램 교반 명령만 차단 ② 히터는 핀삽입 AND 배수문닫힘 AND 명령 ③ 공통해제는 3입력 AND ④ 전원인가·리셋 시 K2·K3 해제펄스 금지 ⑤ 재명령·리셋으로 회로 락을 지우지 않는다.
> **코드 대조 결과 ④는 현행 R2가 이미 충족한다**(§7 Q5·§8-③). 위반이 남은 것은 ①뿐이다.
> ★**반영 [2026-09-22, 구현현황 §0.33]** — ①의 원문(벤더 X001)은 *"새 이상선을 급수·배수·히터·분쇄 **허가**로 연결하지 않음"* 이다. 회로 허가선을 새로 끊거나 풀지 말라는 뜻이다. 벤더 `controller.c` 479 는 에러 단계에서 히터·교반·분쇄를 모두 끈다. 그래서 R2 의 전부 정지는 벤더와 같다. 정정한 것은 에러 중 **팬 유지**(G1·G2), 해제형(E01·E02)/래치형 **해제 규칙**(G3), **`last_err`**(G4)다.

## 4. 영역별 변경 상세

### 4.1 공통 초기화 (ST01 / TB-M01~M03)

- **신규**: UE1 TCA9534 **@0x20** 초기화를 `출력(0x01)=0x00 → 극성(0x02)=0x00 → 방향(0x03)=0x58` 순서로 기록하고 리드백 검증. 불일치 시 EX12/E12로 낙하하고 **새 요청 출력을 내지 않는다.**
  - 현재 `Devices/ExtGpio/tca9554.c`는 `TCA9554_ADDR_BASE 0x38`(TCA9554**A**) 전제 → **0x20은 plain TCA9534 베이스**라 주소 매크로 분리 필요.
  - 방향 `0x58` = P3·P4·P6 입력 / 나머지 출력. 출력 P0·P1 반복설정, P2 시작, P5 준비, P7 복귀 / 입력 P3 이상, P4 완료, P6 급수허가.
- ✅ **초판 정정 — “전원 인가 시 K2·K3 해제펄스 금지”는 현행 R2가 이미 충족한다.**
  `sch/R1/FINAL NETLIST.NET`에서 K1·K2·K3의 `SET-`/`RESET-` 네트(`NetD3_1`·`NetD4_1`·`NetD5_1`·`NetD6_1`·`NetD30_1`·`NetD31_1`)는 1N4148W와 Q5/Q8(2N7002DW)로만 구성되고 **U22(MCU) 핀이 하나도 없다.** MCU에는 래치를 건드릴 물리 경로 자체가 없다.
  → 이 규칙은 **UE1을 붙이는 시점부터** 적용 대상이 된다(Init-RST 경로가 UE1·UW4·Q8B·Q47B로 생기므로). 현행 코드에 대한 조치 사항은 없다.
- ✅ **I2C 주소 충돌 없음**(I13의 절반 해소). R1 넷리스트에 TCA9554 계열은 **U24 하나뿐**(0x3B)이다. `tca9554.h`의 `U8_ADDR 0x39` / `U9_ADDR 0x38`은 R0 잔재이며, R1에서 **U8은 LMC555CMMX**(배출 2분 타이머)다. 다만 **UE1 자체가 현 R1 넷리스트에 미실장**이므로 회로 추가가 선행한다.

### 4.2 가이드 준비 탐색 (ST10·ST11 / R001~R006) — 신규, 그러나 센서는 이미 있다

```
FOR try = 1..3:  dir = (try==2) ? 역 : 정
    교반 30rpm, dir → J28 유효감지 OR 5초(ZG_PREPARE_MS 5000) 경과
    감지 → 즉시 정지, f_guide_ok=1, break      (5.000초 경계는 감지 우선)
    미감지 → 정지 후 1초 대기, 다음 try
3회 실패 → EX1 / E01   (4차 재시도 금지)
준비 구간 감지는 cnt 에 넣지 않는다
```

- ✅ **J28 채널 확정(§7 Q9)**: 넷리스트 `[00033] HS6` = **J28-2 ↔ U24-10(P5)**. R2가 `tb_hall_stir_home`(교반원점 홀)으로 라벨링해 **HW 검증까지 마친 바로 그 채널**이다. 소비 로직만 없었다.
- ⚠️ **응답시간**: TB-B04가 감지→정지 **≤50ms**를 요구하는데 `HallSensor_Update()`는 `StartDefaultTask`(100ms) 폴링이다. `HallSensor_ServiceInt()`(PF9 HALL-INT1, open-drain INT)가 이미 있으므로 **이 경로를 1ms `MotorTick`에서 서비스**하면 충족된다. `zg_inputs.guide_edge_count` / `guide_last_edge_ms`도 같은 경로로 채운다.

### 4.6 온도 락 (ST34·ST35 / P15·P16) — **SW 온도 게이트를 걷어내는 것이 핵심**

| 락 | R1/R2 | R3 | 코드 영향 |
|---|---|---|---|
| K3 (급수·캠 차단) | 60℃ · `GPIO_EXTI_BIMETAL_60`(PF1) | **50℃** (`ZG_HW_WATER_CAM_TRIP_C 50`) | 라벨·주석 재정의 |
| K2 (배수 잠금 + 분쇄 허가) | 80℃ · `GPIO_EXTI_BIMETAL_80`(PF0) | **70℃** (`ZG_HW_DRAIN_GRIND_TRIP_C 70`) | 라벨·주석 재정의 |

- 넷리스트 기준 **`Bimetal-80` 네트 = J7-2 · R35 · R84(→PF0) · U13-2 · U17-2**, `Bimetal-60` 네트 = J38-2 · R85(→PF1) 등. 온도 변경은 **J7/J38에 꽂히는 바이메탈 부품 교체**이고, 펌웨어 쪽은 `main.h` User Label + `gpio_ctrl_t` 라벨 변경(=`.ioc` 재생성)이다. **핀 위치는 불변.**
  - R3 05_HW인터록이 K2 관련 부품으로 든 **U13·U26·U16**과 “U17 교체(SN74LVC1G14)”가 이 네트와 정확히 일치한다 → R3의 “기존 회로”가 R1 도면임을 뒷받침한다.
- ⚠️ **`DJ_TEMP_GRIND_ON_D10`(650)은 재산정이 아니라 폐지 방향이다.**
  `generated/config.h`가 50/70℃ 상수에 `/* Hardware-owned thresholds: references only; MCU edits do not alter UL1. */`를 달았고, README와 `port_contract.json` 모두 **“소프트웨어로 바이메탈이나 K2를 대체하지 않는다”**고 못박았다. 분쇄 허가는 `zg_inputs.grind_allowed`를 **관측**해서 얻고, 프로그램 명령과 AND 해야 한다.
  - `port_contract` 주의: **`U16-24`를 되읽으면 “명령이 있어야 허가가 보이는” 순환 조건**이 되므로 그 경로는 쓰지 말 것.
  - **관측 후보는 이미 R2에 있다** — PF0(`Bimetal-80` → R3에서 70℃). `dongjak.c:592`가 이미 이 엣지를 안전 폴백으로 쓰고 있다. 이 핀을 `grind_allowed`의 1차 관측원으로 제안할 수 있다(I01 회신 필요).
    ★현재: 그 폴백은 `DJ_COOL_USE_BIMETAL80`=0 으로 비활성(`dongjak.c:776`), 관측은 `dj_grind_allowed()`=(PF0==0)&&(PF3==0)(`dongjak.c:225`, N2 해소)로 옮겨졌다.
- ⚠️ **`DJ_COOL_USE_BIMETAL80` 근거 상실**: 식힘 분쇄 OFF(센서 80℃) 판정에 PF0 하강엣지를 OR로 쓰는데, **PF0가 70℃ 접점이 되면 OR가 실제보다 이르게 성립**한다. 제거 또는 채널 재배정.

## 7. Q1~Q10 판정 결과 ★

> 판정 = **확정**(코드·회로로 답이 나옴) / **해소**(질의 불필요) / **유지**(여전히 회신 필요) / **대체**(더 정확한 질의로 교체)

### Q1 — R3의 “기존 펌웨어”가 우리 R2 코드인가 → **확정: 그렇다. 단, 더 큰 결정이 딸려 나온다**

근거 3가지.

1. `board/port_contract.json`의 `gpio_reference_only` 핀 목록이 R2 `Inc/main.h`와 **전부 일치**한다.
   교반 PE8/PE11/PE12/PE14 · 분쇄 PE7/PE9/PE10/PE13 · 히터 PA12 · 급수센서전원 PE2 · 배수문 PC6/PC7+PE4 · 배출문 PC8/PC9+PE3 · 도어홀 PF2~PF5 · 수위 PF6 · 타이머 PF8 · 온도 PC0~PC2 · I2C PB6/PB7 · UE1 0x20/config 0x58.
2. R3 05_HW인터록이 든 부품(U13·U16·U17·U26·K2 TQ2-L2-5V)이 `sch/R1/FINAL NETLIST.NET`과 일치한다 — `Bimetal-80` 네트에 **U13-2·U17-2가 실제로 물려 있다.**
3. `README.md` — “개발사 시험용 애플리케이션은 복사하거나 수정하지 않았습니다”, “실제 기판에 기록할 **시작 코드·핀 적용·주변장치 연결·최종 실행 파일은 아직 완료하지 않았습니다**”. `port_contract`의 `PLATFORM` 항목(시작 코드·클록·주변장치·링커·핀 적용표)도 미승인 상태로 개발사 몫이다.

⚠️ **다만 두 가지가 딸려 나온다.**
- **도면 리비전 차이** — `port_contract.schematic_basis = "FoodDisposal_260906-1 / U 수정 연결도 15판"`, 우리 회로 근거는 `sch/R1`(260806 대조표). **260906 도면 대조가 선행**해야 한다.
- **§0.1의 A안/B안 결정** — 제로지오가 `controller.c`(`zg_tick`)로 공정 FSM을 이미 작성했다. 이식할지 자체 구현할지가 최우선 합의 사항이다.

### Q2 — 195/190℃가 센서값인가 → **확정: 온도센서 측정값. 단, 질의는 “Rfixed”로 대체된다**

- 사용자 확인: “195/190은 동작 시나리오 분쇄 과정에서 **온도센서에서 일정시간 측정되는 온도범위**”.
- `generated/config.c` — `heater_off_c = 195U /* P34 */`, `heater_on_c = 190U /* P35 */`, 단위 **정수 ℃**.
- 조치: `DJ_TEMP_HEATER_OFF_D10 1170 → 1950`, `DJ_TEMP_HEATER_ON_D10 1140 → 1900`.
- ✅ R2 `thermistor.c`는 **이미 이 요구를 예상하고 만들어졌다** — 헤더 주석에 “the vendor sheet STOPS at 150C, but the **동작 scenario must read up to 200C**”라고 적고 160~200℃ 행을 Adafruit 곡선으로 확장, 210/220℃를 외삽해 200℃ 보간 여유까지 뒀다.

⚠️ **대신 새 질의가 생긴다 — `THERM_R_FIXED` 실측값.**
- `thermistor.c:7` `#define THERM_R_FIXED 10000.0f /* R107/R111/R109 pull-down [ohm] */`, 헤더는 “bench-confirmed 10k, **NOT the 1k an earlier BOM read suggested**”.
- 그런데 `FINAL NETLIST.NET`의 BOM은 **R107/R109/R111 = 1K/1608**이다.
- 이 차이가 P34/P35 구현 가능 여부를 가른다. 10k면 150~200℃가 **약 46 counts**뿐이라 **190↔195℃ 히스테리시스 밴드가 1~2 ADC count**다. EMA(`g_therm_filter_alpha` 0.4) 잡음에 묻혀 히터가 채터링한다(TB-F07이 바로 이 항목을 FAIL로 규정). 1k면 같은 구간이 약 26 counts라 여유가 있다.
- ⚠️ 또한 **160~200℃ 행은 벤더 미검증(Adafruit 곡선 차용), 210/220℃는 외삽**이다. 195℃를 제어 기준으로 쓰려면 **벤더 >150℃ 데이터 또는 실측 교정**이 필요하다.
- → **N1**: Rfixed 실측 재확인 + >150℃ 구간 교정. 이것이 Q2를 대체한다.

### Q3 — 실제 70℃의 센서 환산값 → **대체: 환산이 아니라 SW 온도 게이트 제거**

- `generated/config.h`: `/* Hardware-owned thresholds: references only; MCU edits do not alter UL1. */` 아래 `ZG_HW_WATER_CAM_TRIP_C 50` / `ZG_HW_DRAIN_GRIND_TRIP_C 70`.
- `README.md`: “50도·70도는 바이메탈 회로 선정값입니다. 생성 코드의 해당 상수는 **회로 기준을 기록하는 참조값**이지, 소프트웨어로 바이메탈이나 K2를 대체하는 값이 아닙니다.”
- → `DJ_TEMP_GRIND_ON_D10`(650)로 분쇄를 게이팅하는 현 구조는 R3 원칙과 어긋난다. **`grind_allowed` 관측으로 교체**.
- → **N2**: `grind_allowed` 관측 경로 확정. `port_contract`가 **U16-24 되읽기를 순환 조건으로 금지**했으므로, **PF0(`Bimetal-80` 네트, R3에서 70℃)** 를 1차 관측원으로 제안한다(`dongjak.c:592`가 이미 안전 폴백으로 사용 중 — ★현재는 `dj_grind_allowed()` `dongjak.c:225` 로 반영, §9.2 N2).

### Q4 — 헹굼 N=3의 가열시간 손실 → **대체: 손실이 아니라 “상한 부재”가 문제**

- `dongjak.c:1197`(현재 `:1461`) — `DJ_IDLE`에서 `start_req` 소비 시 `c->scn_start = now_ms`. **헹굼 포함**이라 R3의 T0 정의와 동일하다.
- 시간 비교: R2 동작 헹굼 2회 = 약 **410초**(앱 `PROFILE_PROD.rinse_end_ms = 6.8분`). R3 회차는 `ZG_HW_MIN_CYCLE_MS = 60000` 이상 + 급수·도어. **N=3이어도 3×60초 + 급수**로, 현행 R2보다 오히려 짧아질 가능성이 크다.
- → 손실 우려는 R2 기준으로는 역전된다. 실제 위험은 **40감지 도달 시간의 상한이 없다**는 점(P·부하 의존, I03 미실측)이다.
- → **N3**: 회차 최대 시간(t_cycle 상한) 규정 요청. 상한이 없으면 T0 120분 안에 가열이 들어가지 못할 수 있다.

### Q5 — 마개 이탈 시 히터를 끄는가 → **범위 축소, 질의 유지** → ★**해소 [2026-09-22, §0.33]**

> ★벤더 0.3.0 `controller.c` 는 X005 를 포함한 모든 에러 단계에서 `out->heater = false` 다(479). 따라서 "R3대로면 마개를 열어도 히터가 계속 돈다"는 X005 detail 문구(*히터·K2·K3 상태를 임의 **해제**하지 않음* = 허가·래치를 풀지 말라)를 잘못 읽은 것이다. 현행 `Jungji_Heater()` OFF 가 벤더 동작과 같다. N4 는 질의할 필요가 없다.

- ✅ “K2·K3 임의 해제 금지”는 **현행 자동 충족**. 넷리스트상 K1~K3의 SET-/RESET- 네트에 U22 핀이 없다(§4.1).
- ✅ “핀 임의 해제 금지”도 캠 미구현이라 현재는 N/A.
- ⚠️ 남는 실질 충돌은 **히터 출력 1건**: `jungji.c:140 Jungji_Heater()`가 `GPIO_OUT_HT_POWER`를 무조건 off + `tb_heat_*` 클리어. R3 EX5의 정지 대상은 “프로그램 교반·급수 지령”뿐이고, 히터 허가 AND(핀+배수문닫힘+명령)에 마개 위치가 들어가지 않으므로 **R3대로면 마개를 열어도 히터가 계속 돈다.**
- → **N4(안전 이의)**: 마개 개방 중 히터 유지가 의도인지 확인. 우리 권고는 “모터·히터 출력은 정지, 락·핀·허가 상태는 손대지 않음”으로 분리.

### Q6 — 110분 교반 40rpm 폐지가 맞는가 → **해소: 폐지 지시가 아니라 R3가 모른다**

- `generated/config.c`에 110분 교반 속도 전환 상수가 **존재하지 않는다**(`dry_rpm = 20` 하나뿐). R3 ST38도 “가열 구간 20rpm 패턴 유지”.
- R2의 27→40 변경(구현현황 §0.9, 2026-08-26)은 R3 문서·코드 어디에도 흔적이 없다.
- → 별도 질의로 두지 않고 **N5로 통합**.

### Q7 — 건조 교반 20rpm (정5+정지2)×5 → 역3 회귀가 맞는가 → **해소: R3의 기준선이 R2의 2026-08-26 이전이다**

결정적 증거 3개.

| `config.c` | 값 | R2의 2026-08-26 **이전** 값 |
|---|---|---|
| `dry_forward_ms` / `dry_stop_ms` / `dry_forward_group` / `dry_reverse_ms` | 5000 / 2000 / 5 / 3000 | `DJ_STIR_FWD_MS` 3000 / `STOP_MS` 2000 / `FWD_REPS` **5** / `REV_MS` 3000 |
| `rinse_forward_ms` / `rinse_stop_ms` / `rinse_reverse_ms` | 3000 / 1000 / 3000 | 25rpm **CW3 / 정지1 / CCW3** (2026-08-25 이전) |
| `purification_on_ms` / `purification_off_ms` | 10000 / 5000 | **“구 10/5s 내부정화”** (2026-08-17 이전) |

그리고 `README.md`가 직접 말한다 — “건조 중 교반 정회전도 5초로 맞추며 **기존 2초 정지·5회 묶음·역회전 3초는 유지합니다**.” 즉 제로지오는 5회 묶음·역3초를 **‘기존’(=우리 R2)** 으로 믿고 있는데, R2는 2026-08-26 지시로 그 패턴을 폐지했다.

→ **R3는 새 지시를 한 것이 아니라, R2의 2026-08-15 ~ 08-26 지시 반영분을 모르는 상태에서 정회전 3→5초만 바꾼 것이다.**

### Q8 — 공기정화팬 10/5s 회귀와 팬 정체 → **확정: 팬 = `FAN_EXHAUST`(PG2), 값은 Q7과 같은 원인**

- 넷 매핑 확정: 공기정화팬 = `FAN_EXHAUST`(PG2) / 방수팬·환풍팬 = `FAN_VAPOR`(PB15) / 모터 냉각팬 = `BLDC_FAN`(PG1).
- `purification_on/off = 10000/5000`은 R2가 2026-08-17에 15분/2분으로 바꾸기 **이전** 값 → Q7과 동일 원인.

### Q9 — J28 = HS6인가 → **확정: 그렇다**

```
[00033] HS6
        J28        2       2              PASSIVE     533980371
        U24        10      P5             I/O         TCA9554APWR
```

R3가 말하는 “J28 2번 원신호”가 R2의 **HS6 = 교반원점 홀센서**(`tb_hall_stir_home`)다. 2026-08-15에 **HW 검증 완료**됐고 소비 로직만 없던 채널이다(구현현황 §0.5 “HS6/HS7/HS8은 센서는 정상, 소비 로직이 미구현”).

→ 준비 탐색·cnt 계수를 **기존 U24 경로로 바로 구현할 수 있다.** 제약은 응답시간뿐이며 PF9 INT 경로로 해소된다(§4.2).

### Q10 — 135분 백스톱 폐지 시 스톨 위험 → **해소: 위험 없음**

`tdoor.h`에 `TDOOR_OPEN_MAX_MS = TDOOR_CLOSE_MAX_MS = 14300U` 하드 상한이 드라이버에 있다. 구현현황 §0.55 9-1도 “배출문이 14.3초 하드 상한을 가져 **무한 구동 자체가 없다** → `DJ_DISCH_DOOR_NO_TIMEOUT` 도달 불가”로 이미 정리했다. → **초판 리스크 표에서 삭제.**

### 14.5 이것이 뜻하는 것 — 개정 2 결론의 수정

1. **§0.1 A안/B안 → 사실상 B안.** 제로지오 `controller.c`는 `hw_prepare_ack`·`hw_cycle_complete`·`hw_stir_fault`·`hw_water_allowed`·`common_release_authorized` 등을 **회로에서 받는다고 가정**한다. REV02에는 그 회로가 없으므로 A안을 택해도 `board_port.c`가 **UL1 상당(준비 탐색 한도·cnt·t_cycle·과속·순이동)을 MCU로 구현**해야 한다. 그러면 R2 시나리오 계층을 버리고 얻는 이점이 거의 없다.
2. **§7 Q3 / N2(`grind_allowed` 관측)** — REV02는 U15·U26이 분쇄 EN을 하드웨어로 AND 하므로 MCU는 `M1_ENABLE`(PE7)만 내면 된다. 관측 자체가 필요 없다. 다만 "허가가 없어 안 도는 것"과 "고장"을 구분하려면 **PF0(`Bimetal-80`) + `WHALL_CLOSE`(PF3)를 읽어 소프트웨어로 같은 AND를 계산**해 두는 것이 낫다.
3. **§4.9 / C050·C052 공통 해제** — MCU가 할 수 있는 것은 (a) `weight-ADC`로 무게 유효변화 2.108초 연속을 판정해 `f_weight` 래치 (b) 하드웨어가 락을 풀어버린 뒤에도 `f_weight==0`이면 **E08을 내고 정상 완료를 기록하지 않는 것**뿐이다. 락 유지는 못 한다. **R3 절대조건 ③이 회로에서 성립하지 않는다 → N7(회로 담당자 확인).**
4. **C025·C055·C026(핀 캠)** — 하드웨어 없음. 히터 AND에서도 핀이 빠졌다. **보류로 강등**. ★[2026-09-22] **C024**(모음 완료 — 핀 미삽입·캠 전류 0 보장)도 같은 이유로 **보류** — 캠이 없어 보장할 전류 자체가 없고, "배수문 열린 채 종료"는 현행이 이미 그렇다. ★반영 [2026-09-22 §0.36] C026 은 핀 없이 **REV02 2입력(배수문 닫힘 AND 명령)을 소프트웨어 명령에도 AND**(H1) — `W-HALL-CLOSE-1` 이 PF3 와 같은 센서(J6)라 회로와 일치.
5. **C001·C065·H3·H5(UE1)** — 대상 하드웨어 없음. `ue1.c` 이식 불필요. **삭제**. ★[2026-09-22 §0.36] **C027**(UE1 P7 교반 허가 복귀)도 같은 이유로 삭제 — 요구의 실질(헹굼 정상 종료 뒤에만 가열·교반)은 흐름 순서로 충족.
6. **C004·C046·H7·H8(8버튼)** — 하드웨어 확보(U31/J27). 배정만 확정하면 착수 가능. **선행조건 완화**.
7. **C049·H9(배출 타이머 상태)** — `discharge_timer_done`은 PF8(`TIMER-OUT`) 엣지로, `discharge_owner`(회로 구동 중)는 **관측 핀이 없다** → U33-2Q(mux SEL)를 MCU가 읽을 수 없다. `TIMER-OUT` 엣지와 배출문 홀로 소프트웨어 추정. → N7에 포함.
8. ★해소(§0.33) **C063·Q5(마개 이탈 시 히터)** — 히터는 이제 하드웨어 AND(배수문 닫힘)로만 묶여 있어 마개 이탈과 무관. 판정 불변(히터 출력 1건 충돌).

### 14.6 온도 측정 분해능 — N1 후속 (확정된 문제)

R107/R109/R111 = **10K** 확정. `thermistor.h` 주석대로 150~200℃가 **약 46 count**, 190↔195℃는 **1~2 count**. EMA(alpha 0.4)로도 히스테리시스 밴드가 잡음 폭 안에 들어간다.

선택지: ① 195/190℃ 대신 **넓은 밴드**(예: 190/180)로 히스테리시스 재설정 — 사양 변경 합의 필요 ② 고온 채널만 **분압 재설계**(1K 또는 상단 저항 추가) — 회로 변경 ③ **PWM 듀티 제어**로 전환해 ON/OFF 히스테리시스 자체를 없앰 — 펌웨어 변경. → **N11**.

## 17. 2026.09.21 변경 — 시간 패턴 → 회전수 운전

### 17.1 한 줄 결론

**교반·분쇄의 모든 시간 패턴(정5s/정지2s, 정3/정지1/역3/정지1, 역4s/정지2s)이 폐지되고, "교반 가이드 실제 2회전 + 정지 2초 = 1회 운전" 이라는 회전수 단위로 전면 교체됐다.** 제로지오는 이를 위해 HW 무관 순수 로직 `rotation.c/h`(`zg_rotation_tick`)를 새로 써서 보냈다. 우리 쪽 결과는 세 가지다.

1. **2단계(§0.13)에서 만든 `dj_stir_alt_tick()` 4구간 패턴과 `공통헹굼_모듈_구조R3.md` §8의 `Rinse_StirTick()` 재사용 계획은 폐기**된다. 5단계는 "종료 판정만 시간→cnt" 가 아니라 **교반 구동 자체를 회전수 엔진으로 교체**하는 작업이 됐다. 1단계 상수 개정(C034 5s/2s/120s)도 추적용으로 강등.
2. **위치 피드백이라는 새 입력이 필요하다.** `stir_position_ticks`(CW+/CCW−)·`motion_feedback_valid`·`stir_at_rest`·`grind_at_rest` — REV02에 엔코더는 없다. M2 FG(PF12)×DIR 부호 누적 + HS6 원점 교정을 제안한다(N13). **I02 1차 실측(주기 3.10 s, `I02_엣지실측_기록R3.md` §7-①)의 미해결 질문(가이드가 출력축 1:1인가)이 그대로 P54(tick/회전)의 전제**다.
3. **좋은 소식** — ① 110/120분 시계의 기산점이 "최초 히터 ON 명령 성공(`heater_since`)" 으로 확정되어 **I07·N3가 동시에 해소**됐다. ② 모든 스트로크가 가이드 2회전 이상이므로 **§7-④의 "스트로크 3 s < 가이드 주기 3.1 s → cnt 정체" 위험이 구조적으로 사라진다.** ③ 헹굼 10회 운전 × 2회전 = 20회전 = **cnt 20 감지와 1:1** — HS6 엣지가 곧 회전수다.

### 17.6 위치 피드백 설계 제안 (N13 — 확정 전 착수 금지)

REV02에는 교반 위치 센서가 없다. 쓸 수 있는 신호는 둘이다.

| 신호 | 분해능 | 장점 | 단점 |
|---|---|---|---|
| **M2 FG (PF12)** | 극쌍 × 49 펄스/가이드 회전 (실측 필요, I03) · ★실측 **822**/날개 1회전(감속 1:82×1.2, §0.22) | 고분해능. `BldcCtrl`이 이미 계수 | 부호 없음 → DIR 명령으로 부호 부여. 제동 반동·슬립에서 누적 오차 |
| **HS6 (J28-2, 교반 원점 홀)** | 1 엣지/회전 (I02 실측: 정·역 대칭, 깨끗) | **R3 "감지" 정의와 동일** — 20회전 = cnt 20 | 2회전 판정이 ±1회전 양자화. 정지 위치가 매번 자석 위 |

**제안: FG×DIR 누적을 주(主), HS6를 회전 경계 재동기로.** `stir_position_ticks`는 FG 카운트에 DIR 부호를 붙여 누적하고, HS6 상승엣지마다 `position`을 가장 가까운 `ticks_per_revolution` 배수로 스냅한다. 100회 운전 후 누적 오차를 벤치에서 잰다. **P54 = FG 펄스/가이드 회전**은 I02 §7-① (a)/(b) 판별(run D)이 끝나야 정해진다 — 가이드가 출력축 1:1이 아니면(주기 3.10 s ≠ 2.0 s) P54는 극쌍×49가 아니다.

대안(단순안): `ticks_per_revolution = 1`, `position = HS6 엣지 × DIR 부호`. rotation.c 그대로 돌고 P54 실측이 필요 없다. 다만 "2회전 후 정지"가 자석 위치에 종속되고 `motion_feedback_timeout_ms`가 1회전 시간(2~3.1 s)보다 커야 하므로 `>2000` 조건이 빠듯하다. **벤치 1차는 단순안으로 엔진을 검증하고, 2차에서 FG안으로 올린다.**
