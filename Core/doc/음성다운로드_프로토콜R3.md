        │── VU: EXIT ─────────────────────────────>│  protocol_r0 복귀
        │<─ VU: RESP(OK, info=성공 슬롯 수) ───────│

## 1. 물리 계층

REV02 넷리스트에 **BLE 모듈이 없다**. `BLE-TXD` 넷은 `TP6 + U22.113(PC12)` 이 전부다.
UART5 는 테스트포인트로만 나오고, PC 의 USB-UART 를 거기 직결한다.

| 보드 | MCU | 방향 | USB-UART |
|---|---|---|---|
| **TP6** | PC12 (UART5_TX) | 장치 → PC | RX |
| **TP1** | PD2 (UART5_RX) | PC → 장치 | TX |
| GND | — | — | GND |

**115200 8N1, 흐름제어 없음.** (2026-09-20 에 9600 에서 변경)

> ⚠ 보율은 **세 곳이 같이** 움직인다: `foodcleaner.ioc` 의 `UART5.BaudRate` ·
> `Core/Src/usart.c` 의 `huart5.Init.BaudRate` · `protocol_r0.h` 의 `PROTO_UART_BAUD`.
> 마지막 것은 주석이 아니라 `Proto_MonMinPeriodMs()` 의 실제 입력이다.
> **앱 쪽 포트 설정도 115200 으로 바꿔야 한다** — 9600 인 채면 앱 통신이 전부 깨진다.

## 2. 소유권 전환 — 왜 R0 안에 넣지 않았나

UART5 의 평시 RX 소비자는 `protocol_r0` 다. 음성 청크를 R0 프레임에 실으려면:

- `PROTO_DATA_MAX` 를 64B → 4KB 이상으로 키워야 하고(디코더 버퍼 RAM 증가),
- PCM 은 랜덤에 가까운 바이트열이라 DLE 이스케이프가 평균 +1.6%, **최악 2배**가 된다.

그래서 **진입만 R0 로 받고, 그 다음부터는 별도 프레이밍**으로 분리했다.

| 단계 | 동작 |
|---|---|
| 1 | PC → `W \| PROTO_CMD_VOICE_UPD(0x32) \| LEN=1 \| DATA=0x01` |
| 2 | `handle_write()` → `VoiceUpdater_Enter()` → `Proto_SendAck()` 가 ACK 를 TX 링에 적재 |
| 3 | `Proto_Tick()` 선두의 `if (VoiceUpdater_IsActive()) return;` 이후 RX 를 건드리지 않는다 |
| 4 | `VoiceUpdater_Poll()` 이 VU 프레이밍으로 직접 파싱 (세션 종료까지 그 안에서 돈다) |
| 5 | EXIT / 15초 무응답 / 진입 실패 → `g_vu.active=0` → `protocol_r0` 복귀 |

ACK 는 TX 링 + 인터럽트로 나가므로 모드 전환과 경쟁하지 않는다.
진입 직후 같은 틱에서 뒤따르는 VU 바이트를 R0 디코더가 먹지 않도록, RX 소진 루프
안에도 `if (VoiceUpdater_IsActive()) return;` 을 한 줄 더 뒀다.

### 진입 조건과 모드 처리

**거부하는 유일한 조건은 `Moeum_IsBusy() || Dongjak_IsBusy()`** — 시나리오가 실제로
돌고 있을 때다(NAK `PROTO_NAK_BUSY`). 세션 동안 defaultTask 가 묶여 센서 폴링과
SenseTick 이 멈추기 때문이다.

마개 위치는 상관없다. 중재자가 100ms 마다 HS1~5 를 디코딩해 모드를 되돌리므로,
진입할 때 아래를 **임시로** 바꾸고 세션이 끝나면 **둘 다 원래 값으로 복원**한다.

```c
s_saved_mode = g_app_mode;   g_app_mode            = APP_MODE_TESTBENCH;
s_saved_dbg  = g_modearb.dbg_disable;  g_modearb.dbg_disable = 1;
```

복원은 모드를 먼저, `dbg_disable` 을 나중에 — 순서가 반대면 그 사이 한 틱에
중재자가 끼어든다.

## 3. VU 프레임 형식

R0 의 DLE 이스케이프를 쓰지 않는 **순수 바이너리**다.

```
 SYNC0 SYNC1 | TYPE | LEN(2, LE) | PAYLOAD[LEN] | CRC32(4, LE)
  0x56  0x55     1        2            LEN             4
 ('V'   'U')
```

| 필드 | 규칙 |
|---|---|
| SYNC | `0x56 0x55`. 깨지면 바이트를 하나씩 밀며 다시 찾는다(`g_vu.resync`) |
| TYPE | 아래 §4 |
| LEN | 페이로드 길이. `0 .. VU_MAX_PAYLOAD(4104)`. 넘으면 프레임을 버리고 재동기 |
| CRC32 | **IEEE 802.3** (reflected, init/xorout `0xFFFFFFFF`) = 호스트 `zlib.crc32` 와 동일값. 대상은 **TYPE + LEN(2) + PAYLOAD** — SYNC 와 CRC 자신은 제외 |

> **CRC32 구현**: 펌웨어는 니블(16엔트리, 64B) 테이블로 바이트당 2회 반복한다.
> 비트단위(8회)보다 4배 빠르고, 2.8MB 전체에 약 0.4초다. **증분 계산**을 지원해야
> 청크마다 이어 돌릴 수 있어 `VU_Crc32Init/Update/Final` 로 나눠 두었다.
> `zlib.crc32` 와 일치함을 빈 입력·4KB·**청크 분할 경로**로 교차검증했다.

## 4. 커맨드

### 호스트 → 장치

| TYPE | 이름 | LEN | 페이로드 |
|---|---|---|---|
| `0x01` | **BEGIN** | 268 | `slot(1) flags(1) rsv(2) data_len(4) data_crc32(4) hdr[256]` |
| `0x02` | **DATA** | 2+N | `seq(2) + PCM[N]`, N ≤ 4096 |
| `0x03` | **END** | 0 | — |
| `0x04` | **DIR** | 532 | 디렉터리 전체(§2) |
| `0x05` | **EXIT** | 0 | — |
| `0x06` | **PING** | 0 | — (응답 `seq` = `VU_PROTO_REV` = 3) |
| `0x07` | **PLAY** | 1 | `slot(1)` — 그 슬롯을 스피커로 재생(검증용) |
| `0x08` | **STOP** | 0 | 재생 중지 |

### 장치 → 호스트

| TYPE | 이름 | LEN | 페이로드 |
|---|---|---|---|
| `0x80` | **RESP** | 8 | `req_type(1) code(1) seq(2) info(4)` |

커맨드 1개당 RESP 정확히 1개. `info` 는 커맨드별 부가값:

| 커맨드 | `info` |
|---|---|
| PING | JEDEC ID (`0xEF4018` 기대). **`seq` 에는 `VU_PROTO_REV`(=3)** |
| BEGIN | 이레이즈한 64KB 블록 수 |
| DATA | 다음에 기대하는 seq |
| END | 장치가 계산한 PCM CRC32 |
| DIR | 받은 532B **전체**의 CRC32 (0x000~0x20F 대상인 `DIR_CRC32` 필드값과는 다르다) |
| EXIT | 이번 세션에 성공한 슬롯 수 |
| PLAY | 그 슬롯의 `DUR_MS`(재생 길이) |
| STOP | 재생했던 바이트 수 |

### 응답 코드 (`vu_code_t`)

| 값 | 이름 | 뜻 |
|---|---|---|
| 0 | `VU_OK` | 성공 |
| 1 | `VU_E_CRC` | 프레임 CRC32 불일치 |
| 2 | `VU_E_LEN` | 페이로드 길이가 규격과 다름. END 에서는 받은 길이 ≠ `data_len`(info = 받은 길이) |
| 3 | `VU_E_TYPE` | 모르는 TYPE |
| 4 | `VU_E_SEQ` | DATA seq 가 기대값과 다름 → **슬롯 재시작** |
| 5 | `VU_E_SLOT` | `slot ≥ 32` 또는 `data_len` 범위 밖 |
| 6 | `VU_E_FLASH` | w25q128 오류(이레이즈/프로그램/검증) |
| 7 | `VU_E_STATE` | BEGIN 없이 DATA/END · 기록 중(BEGIN~END) PLAY · 재생 중 BEGIN(재생은 멈춘다, §5.7) |
| 8 | `VU_E_DATA_CRC` | END 에서 PCM 전체 CRC 불일치 → **헤더 미기록** |
| 9 | `VU_E_OVERRUN` | 받은 길이가 `data_len` 초과 |
| 10 | `VU_E_PLAY` | 재생 실패. `info` 에 `voice_status_t`(1=슬롯범위 2=읽기실패 3=빈슬롯 4=헤더불일치 5=이미재생중) |

## 5. 설계 판단 (왜 이렇게 했나)

### 5.1 stop-and-wait — RX 링이 작아도 되는 이유

청크마다 ACK 를 기다린다. 장치가 플래시를 굽는 동안(페이지 프로그램, 블록 이레이즈
최대 2초) **호스트는 아무것도 보내지 않는다.** 그래서 UART RX 링은 "한 청크를 받는
동안 쌓이는 양"만 감당하면 되고, 로더가 `osDelay(1)` 주기로 비워내므로 실제 점유는
수십 바이트다.

> RX 링을 256 → 1024 로 키운 것은 **로더 때문이 아니라 보율 12배의 결과**다.
> 100ms 틱 사이 최대 유입이 96B → 1152B 가 되어 평시 `protocol_r0` 쪽 여유가 없어졌다.

### 5.2 통신버퍼 256KB 는 불가능하다

STM32F103ZET6 의 SRAM 은 **64KB 전부**이고 현재 약 18KB 를 쓰고 있다. 지시받은
256KB 는 4배 초과라 물리적으로 만들 수 없다. 대신 **청크를 받는 즉시 플래시에 굽는
스트리밍**이라 RAM 은 프레임 버퍼 4.1KB + 헤더 보관 256B 면 끝난다.

### 5.3 헤더를 END 에서야 쓴다

BEGIN 이 헤더 256B 를 미리 받아 RAM 에 들고 있다가, 데이터를 다 받고 **CRC 가 맞을
때만** 슬롯 첫 페이지에 굽는다.

도중에 전원이 끊기면 헤더가 없으므로 그 슬롯은 **"빈 슬롯"으로 남는다** — 반쯤 쓰인
데이터가 유효한 척하지 않는다. 디렉터리를 맨 마지막에 쓰는 것도 같은 이유다(§8.4):
중간에 죽어도 이전 디렉터리가 살아 있고, 그마저 깨지면 슬롯 헤더 32개로 RAM 에서
복구한다(§2).

### 5.4 필요한 블록만 이레이즈

설계서 §8 은 슬롯당 64KB 블록 4개 고정이지만, 짧은 멘트는 1~2개면 끝난다.

```
blocks = ceil((0x100 + data_len) / 64KB),  최대 4
```

블록당 최대 2초라 26슬롯 × 2블록 차이면 무시할 시간이 아니다.

### 5.5 청크 재전송은 없다

NOR 은 프로그램을 되돌릴 수 없다(1→0 만 가능). 이미 구운 청크를 다시 쓸 수 없으므로
seq 가 어긋나면 `VU_E_SEQ` 를 내고, 호스트는 **그 슬롯을 BEGIN 부터 다시** 한다.
슬롯 단위 재시작은 그 슬롯의 블록을 다시 지우므로 항상 안전하다.

> **현 도구**: `vu_link.download()` 는 자동 재시도를 하지 않는다 — NAK 이면 `XactNak` 로
> 전체를 중단하고 EXIT 를 보낸다. 재시작은 사람이 `--slot N --no-dir` 로 한다.

### 5.6 세션이 defaultTask 를 점유한다

`VoiceUpdater_Poll()` 은 활성화되면 **세션이 끝날 때까지 그 안에서 돈다.** 즉 업데이트
중에는 defaultTask 의 센서 폴링과 `Proto_Tick()` 이 멈춘다.

- 내부 대기는 `osDelay(1)` 양보라 **MotorTask(1ms)는 정상 동작**한다.
- 진입 조건이 "시나리오 미운전"이라 멈춰도 잃을 것이 없다.
- 무응답이 `VU_SESSION_TIMEOUT_MS`(15초)를 넘으면 스스로 빠져나온다 — 호스트가
  케이블을 뽑고 사라져도 회선이 영구 점유되지 않는다.

정식 기능이었다면 이 트레이드오프를 택하지 않았겠지만, 1회성 정비 행위라 구조를
단순하게 유지하는 쪽이 이득이다.

### 5.7 재생 검증을 왜 로더 안에 넣었나

굽자마자 **바로 들어볼 수 있어야** 검증이 끝난다. 그래서 PLAY/STOP 을 별도 경로가
아니라 VU 커맨드로 넣었다 — 이미 열려 있는 세션에서 슬롯 번호만 보내면 된다.

재생 자체는 `Speaker/voice.*` 가 한다(TIM2 16kHz TRGO → DAC1 DMA2_CH3 순환,
1024샘플 핑퐁). **비블로킹**이라 ACK 는 즉시 나가고 소리는 DMA 가 흘린다.
호스트는 응답의 `info`(=DUR_MS)로 길이를 알 수 있다.

**SPI1 경합 규약**: 재생기와 로더가 같은 플래시를 읽고 쓴다. w25q128 에는 락이
없으므로 프로토콜로 막는다 — 기록 중(BEGIN~END)에는 PLAY 를 거부(`VU_E_STATE`)하고,
재생 중에 BEGIN 이 오면 재생을 멈추고 거부한다. 둘 다 정비 행위라 동시에 할
이유가 없다.

`EXIT` 는 재생을 먼저 멈추고 나간다 — 검증 재생을 켜 둔 채 평상시 모드로
돌아가면 다음에 누가 플래시를 읽을 때 SPI1 이 겹친다.

### 5.8 호스트가 ACK 를 판정하는 방법

장치는 기본 1초 주기로 모니터링(M) 프레임을 밀어 올리고 있다. 그래서 **버퍼에서
`0x06`(ACK) 바이트를 찾는 방식은 틀렸다** — M 페이로드(온도·상태 바이트)에 `0x06`
이나 `0x15` 가 섞이면 그대로 오인한다.

호스트는 규격대로 `STX~ETX` 를 잘라 DLE 를 벗기고 **`(W, 0x32)` 프레임인지까지 확인**한다.
잘린 M 프레임이 DLE 로 끝나 있으면 이스케이프 상태가 뒤따르는 진짜 ACK 의 STX 를
데이터로 삼켜버리므로, 파서는 **STX 위치마다 독립적으로** 재파싱한다(쓰레기 해석이
몇 개 더 나올 뿐이고 호출자가 type+cmd 로 거른다).

## 5.9 재생 경로 요약 (`Speaker/voice.*`)

| 항목 | 값 |
|---|---|
| 샘플 클럭 | TIM2 PSC=3 / ARR=999, TRGO=Update → **16.000 kHz** |
| 클럭원 | SYSCLK 64MHz = **HSI/2 × PLL16**(HSE 아님). TIM2 는 APB1×2 = 64MHz |
| DAC | DAC1 CH1(PA4), Trigger=T2_TRGO, 12bit 우측정렬, 출력버퍼 ON |
| DMA | DMA2_Channel3, M→P, half-word, **Circular**, 2048 elements, HT+TC |
| 버퍼 | `s_pcm[2048]` 4KB. 반쪽 1024샘플 = **64 ms**. SPI 2KB 읽기 ≈ 1.1 ms |
| 태스크 | `Voice_Task`(freertos.c, stack 512 words). HT/TC → 세마포어 → 반쪽 채움 |
| 시작 | 앰프 ON → 5 ms 세틀 → 반쪽 2개 선채움 → `HAL_DAC_Start_DMA` → TIM2 start |
| 끝 | 꼬리를 중간값(2048)으로 채워 2회 흘린 뒤 정지 → DAC=중간값 → 20 ms → 앰프 OFF |
| 전환(바지-인) | 재생 중 PLAY 가 오면 지금 것을 끊고 새 것으로. 끊는 순간 DAC 를 **8ms 램프**(실기 확정)로 중간값까지 내린다 — 파형 한가운데를 끊으면 계단이 팝으로 들리기 때문(§0.14.9) ★현행 펌웨어: VU `PLAY` 는 `VOICE_PRIO_NORMAL` 로 들어가 **끊지 않고 1칸 큐에 넣어 앞 음성 뒤에 재생**한다(`voiceupdater.c` PLAY 처리, `voice.c` `Voice_Play`). 끊는(바지-인) 것은 에러 우선순위 요청뿐 — 문서/GUI 와 불일치, 미결 |

> **★ `.ioc` 에 없다.** TIM2·DMA2_CH3·DAC 트리거는 `voice.c` 가 코드로 직접 잡는다.
> `.ioc` 는 다른 세션이 3단계로 편집 중이고, 셋 다 **핀 배정이 아니라서** 그래도 된다.
> 4단계에서 ioc-6~8 로 정식 반영할 때는 **이 수동 설정과 `DMA2_Channel3_IRQHandler`
> 정의를 걷어내야 한다** — `.ioc` 에서 NVIC 를 켜면 `stm32f1xx_it.c` 에도 같은 심볼이
> 생겨 링크가 깨진다.

`LM4871_Beep` 은 계속 동작한다 — 재생이 끝나면 DAC 트리거를 `NONE` 으로 되돌리므로
기존 소프트 톤 생성 경로가 살아 있다.

## 7. 호스트 도구

```bash
pip install pyserial          # CLI 의 유일한 의존성 (GUI vu_gui.py 는 customtkinter 추가 — requirements.txt)

python voice_updater.py --dry-run           # 변환만 (장치 불필요) → image/slot_NN.bin + directory.bin
python voice_updater.py --gen-table         # 펌웨어 Speaker/voice_table.c 생성
python voice_updater.py --port COM5 --play 4   # 구워진 슬롯 재생만
python voice_updater.py --port COM5         # 전체 26개, 약 4~5분
python voice_updater.py --port COM5 --slot 27 --no-dir   # 슬롯 하나만
```

WAV 디코딩(`wave`)·리샘플·CRC32(`zlib`)는 표준 라이브러리다. Python 3.13 에서
`audioop` 이 제거되어 **리샘플은 직접 구현**했다(선형보간).

| 항목 | 값 |
|---|---|
| 입력 | WAV 44.1kHz · 16bit · mono (26개, 7.4MB) |
| 출력 | 16kHz · 12bit 무부호 · uint16 LE (**2.81MB**) |
| 샘플 변환 | `(s16 + 32768) >> 4`, 0~4095 클램프 |
| 슬롯 매핑 | `ID = BASE[폴더] + (파일번호-1)`, BASE = {1:0, 2:2, 3:5, 4:10, 5:12, 6:18, 7:26} |

> 매핑 BASE 는 **결번 3개(03-02·03-03·07-01)를 세어 둔 값**이라 식이 그대로 성립한다.
> 멘트 텍스트(`TEXT[160]`)는 파일명에서 뽑는다(앞 번호와 괄호 주석 제거).

> **리샘플 한계**: 44.1k→16k 다운샘플에 앤티앨리어싱 저역통과가 없다. 안내 멘트
> 수준에서는 청감 차이가 없어 의존성 없이 갔다. 음질 문제가 생기면 여기부터 본다.

## 8. 검증 순서

`HW미검증_항목R3.md` **1-21**(다운로드)·**1-22**(재생)이 정본이다. 요약:

1. **앱 통신 회귀부터** — 보율이 9600→115200 으로 바뀌었다. 음성보다 이게 먼저다.
2. 배선(TP6=장치TX→어댑터RX, TP1=장치RX←어댑터TX) → 진입 OK.
3. PING 에서 `0xEF4018`. `0xFFFFFF` 면 **SB21/SB22**(/WP·/HOLD 브리지)부터.
4. **슬롯 하나 왕복** (`--slot 27 --no-dir`, 59KB) → 장치에서 `tb_voice_hdr_once` 로 확인.
   전체를 돌리기 전에 이것부터.
5. 전체 26개 → `tb_voice_dir_once` 로 `_slots = 26` 확인.
6. 마개를 시나리오 위치에 둔 채 다운로드 → 끝난 뒤 `g_app_mode` 가 원래대로 복원되는지.
7. 전송 중 케이블 뽑고 15초 → 스스로 빠져나와 앱 통신이 돌아오는지.
